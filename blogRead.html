I Built It. Then I Broke It.

What building a full-stack application actually taught me about architecture, state, APIs, databases, deployment and the difference between code that works and software that lasts.

AUTHOR Prince Tiwari
PUBLISHED 24 Aug 2026
READ TIME 8 min
FIELD Full Stack Engineering
ON THIS PAGE 01 — The problem 02 — Architecture 03 — Frontend 04 — Backend 05 — Database 06 — What broke 07 — Lessons 08 — Final build

There is a strange moment in software development when the project stops being a collection of files and starts behaving like a system.

At first, everything feels easy. Create a component. Add a button. Connect an API. Store something in the database. Refresh the browser. It works.

Then the application grows.

Suddenly the cart needs to survive a login. The user needs to stay authenticated. Products need to come from a real database. Orders need to be stored. Admin actions need protection. The frontend needs to know when the backend failed.

That is where I stopped thinking about individual features and started thinking about architecture.

FIELD NOTE 001

A feature is easy to build in isolation. A product is difficult because every feature has to coexist with every other feature.

01 / THE PROBLEM

Everything works until everything has to work together.

My initial approach was straightforward: build the interface, connect the backend and then add features one at a time.

That works for a small prototype. It becomes uncomfortable when the application starts carrying real state.

Consider a shopping cart.

A cart is not simply an array of products. It has to answer questions:

  • Who owns this cart?
  • What happens when the user logs out?
  • What happens when the browser refreshes?
  • What happens when product information changes?
  • What happens when checkout succeeds?
  • Where does the final order live?

Each question introduces another dependency.

02 / ARCHITECTURE

I needed boundaries.

The application became much easier to reason about after separating responsibilities.

01 CLIENT React / UI / State
→
02 API Node / Express
→
03 DATA MySQL / Queries

The frontend became responsible for presentation and interaction. The backend handled application logic and API communication. The database became the source of persistent data.

That separation sounds obvious when written down. It becomes much more useful when debugging at two in the morning.

03 / FRONTEND

State is where the application starts becoming real.

React made the interface itself relatively straightforward. Components could be reused, pages could be separated and data could be passed where it was needed.

The difficult part was deciding where state should live.

Authentication, cart data, wishlist data and orders were not isolated pieces of information. They influenced different parts of the application.

STATE MODEL REACT

 ├── amount

Thinking about state as separate responsibilities made the application easier to maintain than allowing every component to manage everything itself.

04 / BACKEND

An API is a contract, not just a URL.

My backend exposed REST endpoints for authentication, products, orders and other application functionality.

One of the biggest lessons was that an endpoint should have a predictable responsibility.

Once I started thinking about APIs as contracts, debugging became much easier. If the UI was wrong, I checked the client. If the response was wrong, I checked the API. If the data itself was wrong, I checked the database.

05 / DATABASE

The database remembers what the browser forgets.

Local state is useful for interaction. It is not a replacement for persistent application data.

Products, users and orders need a source of truth that survives refreshes, sessions and different devices.

This is where database design starts affecting the entire application.

THE RULE I KEEP COMING BACK TO If the information matters after the browser closes, it probably belongs somewhere persistent.

Thinking about data ownership early also prevents a common problem: storing the same information in multiple places and hoping they remain synchronized.

06 / WHAT BROKE

Of course, things broke.

The interesting part of building software is not that everything works. It is discovering why something does not work.

01 Wrong data reaching the API

A frontend field name did not match the expected backend variable. The request succeeded, but the data was wrong.

02 State disappearing after refresh

Temporary browser state worked perfectly until the page refreshed. Persistence had to be designed intentionally.

03 Production behaves differently

Local development hides configuration, deployment and environment issues that become obvious in production.

04 UI and data disagree

A successful API response does not automatically mean the interface is displaying the correct state.

07 / LESSONS

What I would do differently now.

The biggest improvement would not be writing code faster. It would be spending more time deciding where the code belongs before writing it.

  1. Define data ownership before building UI.
  2. Keep API responsibilities predictable.
  3. Separate reusable components from page-specific logic.
  4. Design authentication before adding protected features.
  5. Think about production deployment before the final day.
  6. Test failure states, not just successful states.

These are not complicated rules. They are simply easier to learn after experiencing the problems they prevent.

08 / FINAL BUILD

Code that works is only the beginning.

Building a full-stack application changed how I look at software.

I no longer see a website as a collection of pages. I see a system: interfaces, state, APIs, databases, users, failures and decisions connected together.

That is probably the most useful thing I took away from building projects.
