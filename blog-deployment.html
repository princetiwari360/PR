CASE FILE / 04 · DEPLOYMENT

From localhost to the Internet.

The moment your application leaves localhost, a different set of problems begins: environment variables, CORS, production APIs, databases, builds, hosting and configuration.

AUTHOR Prince Tiwari
PUBLISHED 24 Aug 2026
READ TIME 8 min
FIELD Deployment Engineering
ON THIS PAGE 01 — Localhost 02 — Production architecture 03 — Environment variables 04 — CORS 05 — Database 06 — Frontend 07 — Debugging 08 — Lessons 09 — Final thought

“It works on my machine” is not a deployment strategy.

Local development is comfortable.

The frontend talks to localhost. The backend runs on your laptop. The database is sitting right there. Environment variables are already configured. You know exactly where every file is.

Then you deploy.

Suddenly the frontend cannot reach the backend. The database connection fails. An environment variable is undefined. A request works in Postman but fails in the browser.

Nothing about the application changed conceptually. The environment did.

FIELD NOTE 004

Deployment does not magically fix an application. It exposes assumptions that were invisible during local development.

01 / LOCALHOST

Local development hides a lot.

Imagine a React frontend running on one local port and an Express backend running on another.

LOCAL DEVELOPMENT ARCHITECTURE 
Browser
   │
   ├── localhost:5173
   │       ↓
   │    React
   │
   └── localhost:5000
           ↓
        Express
           ↓
         MySQL

Everything is close together. You control the entire environment.

Production is different because each part can live on a completely different server or platform.

02 / PRODUCTION ARCHITECTURE

Production turns one project into several systems.

A typical deployed full-stack application may look more like this:

01 USER Browser
→
02 FRONTEND React / Vercel
→
03 BACKEND Node / API

The backend then communicates with the database separately.

PRODUCTION FLOW FULL STACK 
User
 ↓
React Frontend
 ↓
HTTPS API Request
 ↓
Node + Express
 ↓
Database
 ↓
JSON Response
 ↓
React UI

Once you understand this separation, production errors become easier to reason about.

03 / ENVIRONMENT VARIABLES

Your secrets do not belong in your source code.

Local development often uses environment variables for things such as database credentials, API keys and service configuration.

EXAMPLE .ENV 
DB_HOST=your-host
DB_USER=your-user
DB_PASSWORD=your-password
DB_NAME=your-database

The important idea is that production needs its own environment configuration.

A variable existing in your local `.env` file does not mean it automatically exists on your hosting platform.

REMEMBER Local environment variables and production environment variables are separate configurations.
04 / CORS

The browser suddenly becomes strict.

One of the most confusing deployment problems for beginners is CORS.

Locally, your frontend and backend may be running in a setup where everything appears to work.

After deployment, the frontend and backend often have different origins.

DIFFERENT ORIGINS PRODUCTION 
Frontend
https://your-frontend.com

Backend
https://your-api.com

The backend therefore needs to explicitly allow the frontend origin when appropriate.

EXPRESS CORS 
const cors = require("cors");

app.use(cors({
  origin: "https://your-frontend.com"
}));

CORS is not a problem with React or Express themselves. It is a browser security mechanism that becomes visible when applications live on different origins.

05 / DATABASE

The database needs to exist somewhere you don't control locally.

During development, connecting to MySQL on your own computer is straightforward.

A deployed backend cannot connect to your laptop's localhost database.

The production backend needs access to a database that is reachable from the deployed environment.

THE DIFFERENCE DATABASE 
LOCAL

Node
 ↓
localhost
 ↓
MySQL


PRODUCTION

Node Server
 ↓
Database Host
 ↓
MySQL

This sounds obvious after you understand it. It is surprisingly easy to forget while moving a project online.

06 / FRONTEND

Your frontend also has a production configuration.

One of the easiest deployment mistakes is leaving API URLs pointing to localhost.

LOCAL API 
http://localhost:5000/api/products

That URL works on your computer because your computer is running the backend.

It does not work for a visitor opening your deployed website.

PRODUCTION API 
https://your-api-domain.com/api/products

This is why production configuration should be treated as part of the application rather than something you remember five minutes before deployment.

07 / DEBUGGING

Production debugging is mostly about asking better questions.

When something breaks after deployment, randomly changing code usually makes the problem harder to understand.

I prefer following the request from one end to the other.

DEBUGGING CHECKLIST PRODUCTION 
1. Did the frontend load?

2. Is the API URL correct?

3. Did the browser send the request?

4. Did the server receive it?

5. Did the server return an error?

6. Did the database query work?

7. Is the response what the UI expects?

Browser developer tools are often the first place to look. Server logs are the second. Database logs and direct API testing can then narrow the problem further.

DEBUGGING RULE

Do not ask “Why is it broken?” Ask “At which exact step did the expected behavior stop?”

08 / LESSONS

Deployment taught me to think about environments earlier.

Earlier, deployment felt like the final step of a project.

Now I think about it much earlier.

01 Know where your frontend will live

The hosting environment affects routing, build commands and configuration.

02 Know where your backend will live

Server configuration, ports, environment variables and logs become production concerns.

03 Plan your database

Persistent application data needs a production-ready database and secure credentials.

04 Test the production flow

A successful local request does not prove that the deployed system works.

09 / FINAL THOUGHT

Deployment is where the application meets reality.

Localhost gives you a controlled environment. Production gives you an environment you have to design for.

Different servers. Different domains. Different credentials. Different networks. Real users. Real failures.

That is why deployment is not simply clicking a Deploy button.

It is the process of making sure all the pieces of your application can communicate correctly outside your laptop.
